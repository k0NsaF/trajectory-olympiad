> Это аудит опубликованного Git-состояния, а не локальной рабочей копии и не живой базы Supabase. Перед SQL-миграциями необходимо сверить фактическую схему Supabase и локальный `git status`.

## 1. Технологический стек

- Monorepo npm workspaces: `frontend`, `backend`, `shared`.
- Frontend: React 19, TypeScript, Vite 7, React Router 7, Framer Motion, Lucide, Recharts.
- Backend: Express 5, TypeScript, Zod, Supabase JS.
- Database/Auth: Supabase PostgreSQL и Supabase Auth.
- Сборочные команды на корне: `npm run build`, `npm run typecheck`, `npm test`.
- В опубликованном дереве на проверенном HEAD не обнаружены GitHub Actions workflow-файлы; запрос к списку последних Actions runs вернул `total_count: 0`. Это не подтверждает отсутствие других внешних CI-систем.

## 2. Последние изменения

Последние коммиты на проверенной `main` включают улучшение выбора вузов для сравнения, поддержку дополнительных баллов за олимпиады, управление напоминаниями календаря и интеграцию реестра вузов. HEAD — `c9ec25ea0f`.

## 3. Уже имеющиеся backend-модули

- `profiles` — профиль и настройки.
- `universities` — список, карточка и web-discovery вузов.
- `olympiads` — каталог, сезоны, этапы и статусы.
- `benefits` — сравнение льгот и требования.
- `trajectory` — правиловая подборка олимпиад по профилю.
- `reminders` — CRUD личных напоминаний.
- `achievements` — личные достижения.
- `ai` — RAG-подобное извлечение справочных сведений и ответы через провайдеров.

Основные пользовательские модули уже структурированы по routes/schema/service. Это хорошая основа для поэтапного развития, а не основание полностью переписывать backend.

## 4. Существующая схема БД и миграции

Начальная схема создаёт:

- `universities`;
- `programs`;
- `olympiads`;
- `olympiad_seasons`;
- `stages`;
- `profiles`;
- `benefits`;
- `achievements`;
- `reminders`.

Последующие миграции расширяют безопасность достижений, статусы проверки льгот, требования к данным льгот, поля достижений и настройки профиля.

Миграция реестра вузов добавляет к `universities` сведения об официальных доменах, ИНН/ОГРН, филиалах, регионе и ссылках на официальные страницы. Она также создаёт:

- `university_registry_sources`;
- `university_registry_import_runs`;
- `university_registry_records`;
- `university_external_ids`;
- `university_official_domains`.

Реестровые таблицы закрыты RLS и доступны серверу через `service_role`. Их необходимо сохранить и развивать, не создавая параллельный дубль.

## 5. Авторизация и безопасность

- Supabase Auth уже используется на frontend.
- `signUp` передаёт `emailRedirectTo`, а UI отдельно сообщает о необходимости подтвердить почту, если Supabase не вернул сессию.
- `profiles`, `achievements` и `reminders` защищены middleware `authenticate` и используют пользовательский access token.
- В SQL включён RLS; личные строки ограничиваются `auth.uid()`. Для достижений есть отдельное ограничение полей вставки и запрет обычного обновления.
- Роли `moderator`/`admin` и универсальный RBAC в проверенных модулях пока не обнаружены.

Перед релизом нужно проверить фактический параметр подтверждения email в Supabase Dashboard и redirect URLs; код frontend сам по себе не включает настройку провайдера.

## 6. Существенные разрывы с требованиями V2

### 6.1. Каталоги

- В текущей схеме `programs` имеет базовые поля `university_id`, `name`, `direction`; нет полноценной модели уровня, кода, формы обучения, срока, бюджета/платного мест, стоимости и годовой статистики.
- Отдельные сущности профессий и направлений не обнаружены.
- Нормализованный справочник ЕГЭ и требования ЕГЭ к конкретной программе не обнаружены.
- Таблицы тестов, версий вопросов и результатов не обнаружены.
- Нет полноценной страницы/маршрутов каталогов профессий, направлений, программ и ЕГЭ.

### 6.2. Университетский API

В `universities.schema.ts` список фильтров ограничен `search` и `city`. Текущая функция сервиса загружает записи страницами по 1000 строк, затем загружает программы для всего полученного списка вузов. Для крупного каталога V2 нужны явные серверные пагинация, фильтры, сортировка, лимиты и выборка только данных текущей страницы.

### 6.3. AI-квота и авторизация

Текущий `ai.rate-limit.ts` использует `Map` в памяти процесса и ограничивает 12 запросов за 60 секунд по IP. Это не дневная квота пользователя: состояние теряется при перезапуске, не синхронизируется между экземплярами backend и не привязано к аккаунту. Маршрут `/api/ai/ask` в проверенной версии не подключает `authenticate`.

Для согласованного V2 нужно защищённое использование AI и атомарный дневной учёт в PostgreSQL по `user_id`.

### 6.4. Импорт и модерация

Реестр вузов уже умеет вести источники, запуски импорта и записи-кандидаты, а неоднозначные сопоставления могут отправляться на ручную проверку. При этом в проверенной структуре не обнаружены универсальный кабинет модератора и маршруты проверки/публикации данных для всех сущностей. Нужен workflow для новых направлений, профессий, программ, требований и льгот.

### 6.5. Уведомления

CRUD напоминаний уже есть и пользователь ранее подтверждал работу календаря. В опубликованном дереве не обнаружены полноценный browser push service worker и интеграция MAX. Наличие календарных напоминаний не следует считать подтверждением доставки push/MAX/email.

### 6.6. Frontend/UX

- Текущий `/` перенаправляет на `/trajectory`, то есть публичная образовательная главная отсутствует.
- Основной layout — sidebar/dashboard, а не горизонтальная публичная навигация каталогов.
- Текущие страницы сосредоточены на олимпиадах, вузах, профиле, календаре, сравнениях и ИИ.
- В документах `TECH.txt` и `VISUAL.txt` отражены более ранние требования и тёмно-синяя палитра. Они не являются источником правды для нового фирменного визуала V2.

## 7. Что сохраняем

- npm workspaces и общий пакет `shared`;
- текущий React/Express/Supabase стек;
- Supabase Auth и существующий поток подтверждения email;
- таблицы и UUID legacy;
- реестр вузов и импортный parser;
- olympiads, seasons, stages и benefit-модель;
- существующие календарные напоминания;
- полезные проверки Zod и backend-тесты.

## 8. Что не переносим без переработки

- старую sidebar-компоновку как основной публичный UX;
- текущую загрузку всех университетов/программ без пользовательской пагинации;
- временный AI rate limit по IP как механизм дневной квоты;
- строковое поле `programs.direction` как единственную модель направлений;
- старые демонстрационные данные и даты как подтверждённые актуальные факты без перепроверки источников.

## 9. Ограничения аудита

1. Читался опубликованный GitHub HEAD, а не локальная папка пользователя.
2. Нет прямого чтения живой базы Supabase; SQL-миграции описывают ожидаемую схему, но могли применяться частично.
3. Сборка и тесты не запускались в локальной среде проекта. Нельзя делать вывод, что они проходят.
4. GitHub Actions workflow runs для репозитория на момент проверки не найдены.
5. Создание отдельной ветки через подключённую GitHub-интеграцию было отклонено GitHub с `403 Resource not accessible by integration`; поэтому удалённые файлы и `main` не изменялись.

## 10. Следующий безопасный шаг

Создать локальную ветку `trajectory-v2` от актуальной `origin/main`, внести эти документы и зафиксировать их отдельным коммитом. Затем продолжить работу с UX-каркасом и аддитивной схемой только после проверки live-Supabase schema и локального состояния Git.
